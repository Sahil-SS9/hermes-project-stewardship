## 3. Checkpoint push vs merge vs installation vs activation

These four are separate acts with separate authority. None of them has happened.

| Act | Meaning | Authority | Status |
|---|---|---|---|
| **Checkpoint push** | Publish a branch/commit to the remote so work is backed up and reviewable | Already granted for this branch; the feature branch is backed up remotely (`origin/feat/project-management-stewardship` = `b462249…`, and the parent WIP branch is on the remote too) | Backed up |
| **Merge** | Combine the candidate into another branch (child → parent, or → `main`) and make it part of that branch's history | Plan gate PM-0807/PM-0808; requires green exact-candidate evidence plus Sahil's explicit approval | **Not performed** |
| **Installation** | Put the built artefact into a user environment (plugin install into `~/.hermes`, Desktop plugin into the installed app) | Separate owner approval; explicitly outside this programme's current authorisation | **Not performed** |
| **Activation** | Turn the installed artefact on: enable the plugin, start the service, start scheduling, flip features/autonomy | Separate gate after installation plus soak/pilot evidence (plan §1.1, §5) | **Not performed** |

A rollout is therefore wrong if it treats "green tests", "pushed branch",
"merged", "installed" or "activated" as implying one another. The deployment
decision checklist (`docs/release/0.3.0-deployment-decision-checklist.md`)
consumes them one at a time.
