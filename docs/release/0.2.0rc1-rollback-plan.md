# Dockyard 0.2.0rc1 rollback plan

State: documented and locally rehearsed for database/migration fixtures; no live rollback authorised

## Rollback owners

- Release decision: Sahil
- Execution controller: KENSEI
- Service/runtime recovery: requires explicit infra approval

No owner is authorised by this document alone to restart services, replace live
files, restore production data or push Git history.

## Pre-activation requirements

1. Record exact committed source revisions for Dockyard and host contract.
2. Record SHA-256 for installed `index.js`, `style.css` and `plugin.js`.
3. Export the live Dockyard DB:

   ```bash
   stewardctl --db LIVE_DB export --output NEW_BACKUP_DIR
   ```

4. Restore that export to a new isolated DB and run readiness/smoke checks.
5. Record existing installed plugin bytes and location.
6. Record service/unit configuration and current health baseline.
7. Define maintenance window, operator and rollback deadline.

## Activation strategy

Prefer one bounded local Desktop pilot:

1. install immutable candidate bytes;
2. reload/restart only the explicitly approved runtime;
3. run critical smoke checks;
4. hold scheduler and production migration disabled;
5. observe errors, latency, database integrity and UI critical flows.

## Rollback triggers

Rollback immediately when any occurs:

- readiness or critical smoke failure;
- schema migration error;
- work appears under the wrong project/board;
- duplicate/lost canonical tasks or broken hierarchy;
- API error leakage or authentication regression;
- Desktop plugin fails to mount or blocks existing Hermes use;
- database integrity/checksum mismatch;
- unexplained writer conflict or non-idempotent replay.

## Source/plugin rollback

1. stop only the approved Dockyard/Desktop process;
2. restore the exact pre-activation plugin bytes;
3. restore the previous source/environment reference if it changed;
4. restart only the approved process;
5. verify readiness, plugin mount and existing non-Dockyard Hermes flows.

## Database rollback

For Dockyard SQLite:

1. preserve the failed DB; never overwrite it;
2. restore the verified export to a new path using `stewardctl restore`;
3. verify checksum, schema and integrity;
4. repoint runtime only under explicit approval;
5. retain failed DB and export until the rollback hold expires.

For legacy-to-canonical work migration:

- use the marker-guarded migration snapshot;
- automatic apply failure already restores target and preserves the failed target;
- explicit rollback restores snapshot and preserves the applied target;
- never run the migration tool against an unmarked live home.

## Post-rollback checks

- readiness HTTP 200;
- SQLite integrity `ok`;
- canonical project/board/task counts match pre-activation evidence;
- approval/inbox/notification critical flows work;
- no scheduler or migration process remains active;
- incident record states confirmed effects and unresolved side effects.

## Rehearsal evidence

- operational export/restore round-trip: passed on disposable DB;
- tamper/traversal/symlink rejection: passed;
- real-host migration apply/rollback: passed on disposable Hermes home;
- simulated post-create failure: target restored and failed target preserved.

## Unproven until deployment approval

- exact live service names and paths;
- live database size/duration;
- live Desktop reload/restart procedure;
- production monitoring thresholds and rollback owner availability.

These must be captured from current live state immediately before activation.
