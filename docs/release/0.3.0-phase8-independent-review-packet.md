## 2. Scope and exclusions

State in one paragraph what the candidate changes and what it explicitly does
not change. List exclusions, e.g.: no canonical Hermes Projects/Kanban/Profiles
ownership change; no permanent project/milestone/workflow purge; no scheduler
activation; no installation or activation; deferred backlog as listed in
reconciled documentation.

## 3. Evidence index

For each item, cite the raw log path, the exact command, exit code and
pass/fail/skip counts, and the evidence class (fixture/mock · real Python proxy ·
real vanilla host · installed Desktop). At minimum:

- Python gates from the post-integration checklist (§1 of that document);
- parent-baseline comparison and per-result attribution;
- Phase 7 gate evidence, rerun on the merged candidate;
- Phase 6 gate evidence (per PM-06xx);
- interface checks (export/restore, removal rehearsal, lifecycle matrix,
  authority fail-closed);
- visual/accessibility artefacts and the installed-plugin recordings, with
  their file paths;
- known gaps: GitHub Actions matrix unavailable, any deferred heavy gate, any
  installed-Desktop proof not obtainable.

## 4. Domain reviews (one verdict each)

Every reviewer returns exactly one verdict: `APPROVE`, `APPROVE WITH
CONDITIONS` (conditions itemised and testable), or `REJECT` (with the minimal
reproduction). Reviewers must not approve on the basis of this packet's prose
alone; they must open the cited logs or rerun.

| Domain | Question to answer | Verdict | Conditions / reproduction |
|---|---|---|---|
| Code | Is the delta correct, minimal and consistent with its own contracts? Any dead path, swallowed error or unhandled failure class? | | |
| Architecture | Does the candidate preserve canonical ownership (Kanban owns work, Projects owns identity, Stewardship owns governance) with no second state store and no cross-database atomicity claim? | | |
| Data integrity | Do migration, export/restore, archive/restore and managed-content removal preserve invariants? Is the irreversibility boundary stated truthfully? | | |
| Security | Do privileged operations fail closed without a verified principal? Is capability never conferred by request payload? Are untrusted-content and command-allowlist boundaries intact? | | |
| UX | Are loading/empty/unavailable/offline/validation/conflict/recovery/permission-denied states all reachable and honest? Is any missing backend route ever rendered as a false empty state? | | |
| Documentation | Do README, guides, PRD/roadmap and release records state one ownership model, and do they distinguish DB rollback, irreversible truncation and backup restoration? | | |

## 5. Release-blocking conditions to check explicitly

Reject or condition if any of these is still true (plan §2):

- work enumeration can silently stop at 100 tasks or epics;
- removing a member can hide, orphan or partially transfer work without a
  resumable operation record;
- claimed/running work can be reassigned without an explicit safe handoff
  contract;
- a stale consequence preview can still execute;
- ownership or archive mutation is possible with only a payload actor string;
- Desktop can turn a missing proxy/backend route into a false empty state;
- Stewardship treats its bot registry or member table as the source of profile
  existence;
- existing `dockyard.db` state cannot upgrade and recover from a verified
  snapshot;
- vanilla Hermes integration is tested only with fake adapters;
- critical UI journeys lack real installed-plugin visual evidence.

## 6. Reviewer output shape

```
Candidate:            <SHA>
Verdict:              APPROVE | APPROVE WITH CONDITIONS | REJECT
Scope actually read:  <paths / logs opened, with what was rerun>
Findings:             one per line — severity, file:line, observed, expected, minimal fix
Conditions:           testable, owner, evidence required to clear
Unproven claims:      anything the packet asserts without a reproducible artefact
Independence:         reviewer identity + confirmation of no authorship on this delta
```

## 7. After review

Only after every reviewer has returned a verdict and all conditions are cleared
may PM-0807 (open the child → WIP PR) be considered, and only Sahil may grant
PM-0808 (merge approval). Merge approval still does not authorise installation,
activation or deployment. Do not close a REJECT by editing the packet.
