# v0.3.0 deployment decision checklist

> **Prepared by Lane C; nothing here has been executed or approved.** Deployment
> is not authorised by this programme's current gates. This checklist exists so
> that the decision can be made explicitly, with the prerequisites and the
> irreversibility boundary visible.

## 1. Four separate decisions (do not merge them)

| # | Decision | Who | Precondition |
|---|---|---|---|
| 1 | Merge approval (child → parent WIP, or → `main`) | Sahil | Green exact-candidate evidence + independent review at the candidate SHA + reconciliation of docs |
| 2 | Installation approval (plugin/Desktop artefact into a real environment) | Sahil | 1, plus a rehearsed, reversible install procedure |
| 3 | Activation approval (enable plugin, start service/scheduling, set autonomy) | Sahil | 2, plus soak/pilot evidence in a non-user environment |
| 4 | Deployment approval (wider rollout / cutover) | Sahil | 3, plus rollback rehearsal evidence and a named rollback owner |

A "yes" to one is never a "yes" to the next.

## 2. Prerequisites that must be true before decision 2 (installation)

1. **Candidate identity**: exact SHA, merge base, diff fingerprint, and the same
   SHA present in every log of the packet.
2. **Post-integration gates**: `docs/release/0.3.0-post-integration-test-checklist.md`
   executed on the merged candidate, with per-gate exit codes and raw log paths,
   plus explicit statement of any deferred gate (GitHub Actions matrix, browser
   matrices, installed-Desktop proof).
3. **Parent-baseline attribution**: every result change attributed against the
   actual merge base; `59cd75ca…` retained as historical evidence only.
4. **Independent review**: all reviewer verdicts at the candidate SHA, all
   conditions cleared. A `REJECT` or an unresolved condition stops here.
5. **Documentation reconciliation**: README, canonical-ownership/surface guide,
   lifecycle guide, migration/recovery guide and release records agree; PM-06xx
   claims (CLI recovery commands, Dashboard subset, TUI/messaging limits,
   compatibility revision range) are written down and true.
6. **No hidden live mutation during preparation**: confirmation that the user's
   installed Desktop/plugin, live `HERMES_HOME`s, live databases, gateways and
   services were not touched by any preparation run.

## 3. Backup and migration prerequisites (before touching any real database)

1. Verify the managed content root path for the target profile
   (`<database parent>/project-content`) and back it up **separately** from the
   database.
2. Take a verified Stewardship database export:
   `stewardctl --db <live-db> export --output <new-archive-dir>`, then verify
   the manifest (integrity, size, SHA-256, schema version) and rehearse a
   restore into a throwaway target.
3. Confirm the archive does **not** contain managed content, and state that
   limitation in the rollout note.
4. Record the rollback pair: which database file and which code revision are
   restored together. No in-place schema downgrade is permitted; a
   newer-than-supported schema fails closed.
5. Identify canonical Hermes stores separately (Projects, Kanban, Profiles) and
   confirm the change neither migrates nor mutates them.

## 4. Rollback plan — what each mechanism can and cannot undo

| Mechanism | Recovers | Does not recover |
|---|---|---|
| Restore previous Stewardship DB + previous code together | Rows, schema usage, membership/goal/objective/milestone/workflow metadata, audit history | Removed managed-content bytes; canonical Hermes state |
| Isolated migration rollback (`IsolatedMigrationRunner.rollback`) | A marker-owned isolated target home from its verified snapshot (preserves the mutated target as `-applied`) | Anything outside a marker-owned isolated root; production homes are not authorised here |
| Filesystem backup of the content root | Managed content that existed at backup time | Content uploaded or removed after the backup |
| Managed-content removal | **Nothing** — truncated inodes are gone; the zero-byte `.removing` marker is a marker, not the data. It is not secure erasure and it is not reversible | Data blocks, snapshots, prior backups, copies |

State the irreversibility explicitly in the rollout note: after removal, only a
pre-removal backup of the content root can restore the content.

## 5. Soak / pilot requirements (before decision 3 or 4)

- Run in an isolated installation with disposable homes and databases, unique
  ports and browser profiles; never on Sahil's display or installed app.
- Exercise the critical journeys end to end: onboarding → team change →
  interrupted transfer recovery → archive/restore.
- Observe for a defined period with real (non-fixture) triggers before any
  activation of scheduling or autonomy above level 2.
- Capture: failures seen, retries used, recovery paths exercised, any manual
  intervention, and the exact artefacts (logs, videos, DB snapshots).

## 7. Do-not-ship triggers

Stop and return to the coordinator if any of these is observed:

- any gate green only because a test was weakened, skipped or mocked where a
  real proxy/host was required;
- a removed managed file described as securely erased;
- rollback described as recovering removed content;
- a claim that Stewardship owns canonical work, project identity or profile
  existence;
- an install or activation step performed before its decision row above is
  signed;
- any live mutation of Sahil's installed app, live homes, production database
  or running services during preparation.
