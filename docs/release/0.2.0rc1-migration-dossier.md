# Dockyard 0.2.0rc1 migration dossier

State: isolated migration path built and proven; production migration not authorised

## Source and target

Source:

- a copy of a legacy Dockyard SQLite database containing
  `dockyard_work_items`;
- parent directory must contain `.dockyard-isolated-migration-source` with
  exact content `dockyard-isolated-v1`.

Target:

- a disposable Hermes home with canonical project and board already created;
- root must contain `.dockyard-isolated-migration-target` with exact content
  `dockyard-isolated-v1`;
- target must not be a symlink or live Hermes home.

## Command

```bash
dockyard-migrate-legacy dry-run \
  --source-db SOURCE_COPY/stewardship.db \
  --target-home ISOLATED_HERMES_HOME \
  --snapshot NEW_SNAPSHOT_PATH \
  --project PROJECT --board BOARD

dockyard-migrate-legacy apply \
  --source-db SOURCE_COPY/stewardship.db \
  --target-home ISOLATED_HERMES_HOME \
  --snapshot NEW_SNAPSHOT_PATH \
  --project PROJECT --board BOARD
```

Explicit rollback:

```bash
dockyard-migrate-legacy rollback \
  --source-db SOURCE_COPY/stewardship.db \
  --target-home ISOLATED_HERMES_HOME \
  --snapshot SNAPSHOT_PATH \
  --project PROJECT --board BOARD
```

## Mapping

- `task`, `bug`, `spike`, `subtask` and `epic` become canonical Hermes work.
- initiatives remain Dockyard governance records and are not converted to
  canonical tasks.
- title, assignee, creator, hierarchy, status, labels, evidence references and
  estimate are mapped where represented by the canonical contract.
- deterministic key: `dockyard-migrate:{project}:{legacy_ref}`.
- retries return existing canonical records instead of duplicating them.

## Safety properties

- dry-run performs no target work writes;
- source rows are digested before and after apply;
- target is snapshotted before the first migration write;
- a failed apply renames and preserves the failed target, then restores the
  snapshot automatically;
- explicit rollback preserves the applied target and restores the snapshot;
- missing/invalid markers, symlinks, existing snapshot paths and hierarchy
  inconsistencies fail closed;
- no live migration path is provided by default.

## Proven tests

- reference adapter dry-run/apply/replay/rollback;
- real ProjectKanbanHost migration and snapshot restore;
- missing marker rejection;
- failure after canonical create restores snapshot and preserves failed target;
- successful apply followed by explicit rollback restores an empty canonical board;
- source digest is unchanged throughout.

## Production prerequisites

Before any production migration:

1. identify the live source DB and every current writer;
2. take `stewardctl export` and rehearse restore;
3. stop/drain writers under a separately approved maintenance window;
4. copy the source into a marker-owned isolated proof root;
5. run dry-run/apply/rollback on an isolated target;
6. reconcile source count, mapping count, canonical count and hierarchy;
7. record approved production target paths, ownership and permissions;
8. obtain explicit migration and service-restart approval;
9. take a fresh pre-lift backup;
10. monitor and retain both rollback snapshot and failed-target preservation.

## Current decision

No production database or live Hermes home has been read, changed or migrated.
